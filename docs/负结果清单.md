# 负结果清单：试过但不赚钱 / 被推翻的改动

> 这张表的价值在于**省时间**：每一条都花过几小时到几天。数字均来自本机实测（2×910B4），
> 出处指姊妹仓库 `qwen-ascend` 的轮次文档。**口径不同不能直接比较的地方已标注。**

## 1. 算子/融合类

| 试过的改动 | 结果 | 关键实测 |
|---|---|---|
| **自研 MIX kernel**（msopgen 搭 AscendC 骨架，把 dequant+GEMM 融合） | ❌ 不赚 | 能跑通（1024³ **24.9 TFLOPS**、2048³ 28.4 TFLOPS），但真实形状下裸露 matmul 比现成 `npu_weight_quant_batchmatmul` **慢 4.4×**（gu M=1,N=12800：0.189 vs 0.043 ms）；GM 往返 65.5 MB ≈ 0.070 ms（1872 GB/s）把融合收益吃光 ⇒ 只有 L1 级融合才可能赢 |
| `addcmul` 融合残差注入 | ❌ 更慢 | 复现两次，10240 元素规模**慢约 0.5 ms/步**（第 41 轮） |
| lm_head 改 int8 分块 | ❌ 更慢 | **+1.7 ms/步**（第 40 轮） |
| DeltaNet 用 5-D 广播免掉 `repeat_interleave` | ❌ 更慢 | **慢 0.7 ms**——5 维张量逐元素效率不如物化两次 + 4 维 |
| 四路稠密投影合成一次 GEMM（CAT4） | ❌ 不赚 | 默认关（第 42 轮） |
| `div(rounding_mode="floor")` 求模 | ❌ 慢 | 产生 **252 MiB** 临时张量 |

## 2. MoE 相关

| 试过的改动 | 结果 | 关键实测 |
|---|---|---|
| **按专家分组 + 每专家一次 WQBM 小调用** | ❌ 慢 3.7× | 独占卡、T=128、并集 470/512：逐 token 产线路径 **0.80 ms/token/层**，分组 **2.95**（E-major）/ **3.38**（每专家 `contiguous()`）ms/token/层；940 次调用每次 ~0.40 ms，而单次算子只要 0.050–0.057 ms ⇒ 差额全是簿记算子 |
| 把权重容器改成 **E-major** 只为省 `_wcat` 拷贝 | ❌ 收益极小 | `_wcat`（拷 10 专家 int4 权重）只占每 token MoE 的 **13%**（0.053 ms/次） |
| **`FNX_MOE_FAST`：图内减算子**（silu·mul 全程 bf16、路由从 6 个算子降到 3 个、对角一次 `index_select`、`_scat` 原地乘） | ⚪ 零收益 | 少 8 个算子/层，TPOT **63.7–63.9 vs 对照 63.5–63.7**，`mean_nll` 2.1648 逐位相同 ⇒ 图捕获路径里被删的都是与 Cube **并行重叠**的 Vector 小算子，不在关键路径 |
| 低精度 router / 激活（`FNX_MOE_ROUTER_FAST` / `FNX_MOE_ACT_BF16`） | ❌ 质量不达标 | NLL **2.1858**（门限 2.1748） |
| decode 走 FP32 BMM 候选 | ❌ 质量不达标 | NLL **2.1772** |
| **但**：expert-major 重排 + `GroupedMatmulV5` | ✅ 是正收益 | 单层 T=128：逐 token 44 ms → **7.5 ms**（关键是 GMM 支持三维 batch，WQBM 不支持） |

## 3. 硬件路径类

| 试过的改动 | 结果 | 原因 |
|---|---|---|
| CPU 分担专家计算 | ❌ 不可行 | 鲲鹏 920 **无 AVX-512 / SVE**；实测宿主 `index_select` + H2D 只有 **0.74 GB/s** |
| 专家权重走 PCIe 流式预取 | ❌ 无对象 | 512 个专家**全在 HBM**，没有可流的冷数据 |
| 单进程里让 dev1 也做图捕获 | ❌ 不可能 | 平凡链都失败；单进程跨卡 + 图 replay 会读到**上一个 token 的陈旧 h**（差 54.169%）。⇒ 改成**每卡一个独立进程**后正常 |
| dev1 多放层（LPC=46） | ❌ 差一点 | 只差 **93 MiB** 就 OOM，凑不出来 |
| `FNX_DEQ_ATTN=20` | ❌ OOM | 预反量化注意力权重吃显存 |

## 4. 测量/口径类（不是优化，是"坑"）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 在**被生产占用的另一张卡**上做算子微基准，且没设当前 device | 所有数字虚高 **1.8×**，差点得出"每次调用固定开销 0.6 ms"的错结论 | 独占卡 + `with torch.npu.device(dev)` |
| 用**同一 prompt 连发**测 TTFT | 命中前缀缓存，测出 **58 ms** 的假 TTFT | 每次唯一随机前缀（cold）+ 同 prompt（warm）两档都报 |
| 只用 `pos=0`（S 全零）验证分块与逐 token 一致 | 48 层显示"全部精确"，实际 tok2 才炸 | 必须用**非零状态**验证；1 ulp 归约差会被 MoE topk 放大成 6.9e-2 |
| `max_tokens=2048` 跑 LiveCodeBench 100 题 | **29/100 题被截断**，64% 只是"预算下界" | 报数时标明预算；截断题单独统计 |
| MBPP+ 沿用原版提示词 | 题目无 `starter_code` ⇒ 提示词退化成"读 stdin"，判题器却按脚本调具名函数 ⇒ **1/33 的假象**（修正后 23/33） | 给具名函数提示；**评测前先验证协议自洽** |
| 判题跑在宿主机 python3 | 没有 numpy，`testtype=script` 全部 `runtime` | 容器 venv 内判题 |
| 判题用进程池 | `ProcessPoolExecutor` + `subprocess(preexec_fn=…)` 产生**假 runtime 失败** | 串行进程内判题 |
| 启动脚本被改过却按旧印象报数 | 一次 **15% 的"假回归"**（TPOT 64→74 ms、显存 58.97→59.53 GiB） | 报数前 `pgrep -af` 看实际环境 |

## 5. 一句话总结

**这个项目里真正赚钱的改动只有三类**：把反量化搬进 Cube（算子级）、把逐 token 换成"分块 + 图捕获"、
把内存/搬运结构换掉（E-major + GMM、BF16 连续 KV、稀疏 indexer）。
其余绝大多数"看起来该赚"的融合与微优化，都被**调用固定开销**或**带宽往返**吃掉了。
